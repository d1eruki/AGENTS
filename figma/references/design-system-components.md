# Компоненты, использование и безопасное удаление

## Компоненты

### Варианты

Используй вариант, когда меняется:

- состояние;
- стиль;
- размер;
- тип;
- функциональное поведение;
- композиция, являющаяся стабильной частью API.

Не используй варианты для уникального контента.

### Текстовые свойства `TEXT`

Используй для редактируемого контента.

Учитывай:

- свойства `TEXT` внутри набора компонентов имеют общие определения и значения по умолчанию;
- варианты не должны различаться случайными демонстрационными текстами;
- уникальное содержимое экранов хранится в переопределениях экземпляров;
- реальные примеры в документации лучше показывать отдельными демонстрационными экземплярами;
- после добавления свойства нужно проверить самый длинный текст.

### Логические свойства `BOOLEAN`

Добавляй только для реальной настройки видимости или состояния.

Не создавай свойство `BOOLEAN`, если слой присутствует во всех существующих случаях.

### INSTANCE_SWAP

Используй, если вложенный компонент действительно должен свободно меняться.

Если вложенный элемент однозначно определяется вариантом, закрепи его внутри варианта. Общий `INSTANCE_SWAP` может уничтожить правильные значения по умолчанию для отдельных вариантов.

Не создавай отдельный вариант для каждой пиктограммы.

### Связанный контент

Считай значения связанными, если независимое изменение одного создаёт визуально правдоподобное, но фактически неверное состояние.

Для связанного контента:

- определи единицу согласованного изменения;
- не публикуй неполный API;
- используй вложенный компонент для заменяемого графического ресурса;
- открывай `INSTANCE_SWAP` только на уровне размещённого экземпляра, не превращая обычный вектор в публичную настройку;
- документируй внутренний вспомогательный компонент понятным техническим именем и не выдавай его за отдельный продуктовый компонент;
- проверь сочетание по умолчанию и хотя бы одну замену, если альтернативный ресурс доступен.

QR-код, штрихкод и подобная графика могут сохранять собственные цвета и внутреннюю векторную геометрию. Систематизируй контейнер и API, но не нормализуй содержимое графики как обычный интерфейсный макет.

### Слоты

Используй слот, когда компонент должен принимать произвольное структурное содержимое, которое нельзя выразить свойствами `TEXT`, `BOOLEAN` или `INSTANCE_SWAP`.

Не заменяй обычную предсказуемую структуру свойством слота без необходимости.

### Старые компоненты

Удаляй старый компонент только после проверки:

- все требуемые потребители заменены;
- новых потребителей старого мастер-компонента нет;
- переопределения перенесены;
- удаление входит в запрос.

Не создавай скрытый архив без согласования. Если старая версия должна сохраниться, сообщи точное место и причину.

### Изменение существующего мастер-компонента

Если добавляется новый вариант:

- по возможности сохрани исходный мастер-компонент как один из вариантов;
- не пересоздавай его без необходимости;
- проверь старые инстансы;
- посчитай, сколько потребителей переключено;
- посчитай, сколько намеренно осталось;
- проверь их переопределения и замены вложенных экземпляров;
- проверь отсутствие сломанных экземпляров.

Если старый второстепенный, компактный или другой компонент совпадает с существующим набором по правилам размеров и структуры, предпочти перенос в вариант этого набора. До удаления старого мастер-компонента:

- сопоставь старые свойства с новым API;
- замени все подтверждённые экземпляры в продукте;
- проверь размещения в документации и вложенных потребителей;
- повтори поиск по ID старого мастер-компонента;
- только затем удаляй старый мастер-компонент по явной команде.

## Аудит использования и безопасное удаление

### Сначала определи, что именно указано ссылкой

Не называй узел компонентом до чтения его типа и структуры.

Ссылка пользователя может указывать на:

- документационную обёртку;
- контейнер предпросмотра;
- мастер-компонент;
- набор компонентов;
- отдельный вариант;
- экземпляр;
- обычную несвязанную копию, визуально похожую на компонент.

Если обёртка содержит мастер-компонент, раздели их в отчёте и назови оба ID. Фраза «удалить этот узел» означает удаление указанного поддерева, поэтому до операции перечисли все значимые сущности, которые исчезнут вместе с ним.

### Проверяй использование по канонической связи

Основной критерий использования — связь экземпляра с конкретным мастер-компонентом через `mainComponent`, ID или ключ компонента.

Не считай достаточным:

- совпадение имени;
- визуальное сходство;
- нахождение элемента в документации;
- наличие вложенного библиотечного экземпляра внутри мастер-компонента;
- количество копий предпросмотра в документации.

Проверяй все страницы файла, входящие в область аудита. Если инструмент загружает страницы отдельно, сначала получи полный список страниц, затем проверь каждую независимо. Когда инструмент это поддерживает, выполняй независимые проверки страниц параллельно.

В результате разделяй:

1. реальные экземпляры в продукте;
2. вложенные экземпляры внутри других мастер-компонентов;
3. размещения в документации;
4. сам мастер-компонент;
5. обычные или отсоединённые похожие элементы.

### Не теряй скрытые потребители

Оптимизация, пропускающая невидимых потомков внутри экземпляров, допустима для быстрого первого прохода.

Она не подходит как единственное доказательство перед удалением. Перед выводом «не используется» выполни контрольный точный проход, не пропуская скрытых потомков экземпляров и скрытые состояния.

Формулируй нулевой результат точно:

- сколько страниц проверено;
- учитывались ли скрытые слои;
- проверялась ли связь с мастер-компонентом;
- выполнялся ли расширенный поиск обычных несвязанных копий.

### Учитывай внешних потребителей

Отсутствие инстансов в текущем файле не доказывает отсутствие потребителей в других файлах.

Перед удалением локального мастер-компонента:

- проверь статус публикации;
- определи, является ли компонент частью опубликованной библиотеки;
- если внешние файлы недоступны, явно сообщи границу аудита;
- не утверждай, что внешних потребителей нет;
- получи явную команду на удаление опубликованного компонента.

### Чек-лист перед удалением

Удаляй мастер-компонент или поддерево документации только после проверки:

- точного ID, типа, имени и страницы;
- предков и значимых потомков;
- непосредственных и вложенных экземпляров на всех страницах;
- скрытых экземпляров и состояний;
- обычных и отсоединённых похожих элементов;
- статуса публикации и возможных внешних потребителей;
- явной команды пользователя;
- того, какие объекты будут удалены вместе с обёрткой.

Для рискованного удаления сохрани доступную точку восстановления: историю версий, обратимую операцию или заранее согласованную резервную копию.

### Проверка после удаления

После операции:

1. Убедись, что каждый удалённый ID больше не разрешается.
2. Повтори точный поиск по ID мастер-компонента или ключу.
3. Повтори расширенный поиск по имени и роли.
4. Проверь родительский Auto Layout, размеры и соседние блоки документации.
5. Проверь отсутствие пустых промежутков, нежелательной перестройки и сломанных экземпляров.
6. Верни полный список `removed node IDs`.

Нельзя считать удаление проверенным только потому, что API вызов завершился успешно.
