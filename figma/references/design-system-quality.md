# Организация, коммуникация и проверка

## Системные элементы платформы

Если используются системные строки состояния, индикаторы главного экрана, клавиатуры, панели навигации или другие системные элементы:

- используй официальную библиотеку платформы;
- не создавай собственную копию без необходимости;
- не отсоединяй экземпляр;
- сохраняй системные размеры и поведение;
- размещай через правильный контейнер компоновки;
- не используй абсолютное позиционирование без поведенческой причины.

## Именование

Сначала следуй существующим правилам проекта.

Если правила отсутствуют, используй:

- понятные названия компонентов;
- `Property=Value` для вариантов;
- единый формат документации;
- семантические названия внутренних слоёв;
- иерархию имён через `/` для переменных и стилей;
- названия по роли, а не по содержимому конкретного экрана.

Примеры внутренних ролей:

- `Header`
- `Title`
- `Message`
- `Icon`
- `Content`
- `Actions`
- `Container`
- `Icon Wrapper`

Не переименовывай слой только ради единообразия, если он не входит в область работы.

Имена страниц и секций являются изменяемым пользовательским контекстом. Перед отчётом используй текущие имена из файла, а не ранние названия из переписки. Для автоматизации сохраняй ID вместе с прочитанным текущим именем и проверяй, что ID ещё разрешается.

## Организация страницы дизайн-системы

Группируй документацию по семантическому домену и роли компонента, а не по совпавшему слову в названии.

Например, карточка предметной области продукта, обычная карточка содержимого, карточка уведомления и контейнер адреса могут содержать слово `Card` в названии, но не обязаны находиться в одной категории.

Перед перестановкой:

1. Найди обёртки документации и мастер-компоненты внутри них.
2. Сформулируй критерий принадлежности к новой категории.
3. Назови одноимённые сущности, которые исключены по другой роли.
4. Перемещай существующие обёртки документации, не пересоздавая мастер-компоненты.
5. Сохраняй ID компонентов и их наборов.
6. Создавай категорию как прозрачный Auto Layout в существующей иерархии.
7. После переноса проверь порядок, высоты родителей, перестройку соседних категорий и сломанные экземпляры.

Организационная правка страницы не должна менять API компонентов, экранные экземпляры или внешний вид самих компонентов.

## Ограничение области

- Не расширяй аудит за пределы запроса.
- Не меняй визуально похожие, но функционально другие сущности.
- Не перестраивай соседние элементы без необходимости.
- Не меняй текст, если задача структурная.
- Не создавай параллельные экраны, если пользователь просит изменить существующие.
- Всегда работай в указанной копии или ветке.
- Не публикуй библиотеку и не изменяй внешние файлы без отдельной команды.
- Не удаляй материальные объекты на основании предположения.

## Коммуникация

Перед изменениями кратко сообщи:

- что проверяется;
- что входит в область;
- что не будет затронуто;
- критерий завершения.

Во время длинной работы сообщай текущий этап без лишнего внутреннего жаргона.

Не используй абстрактные формулировки без расшифровки. Всегда объясняй:

- какие объекты затрагиваются;
- какое различие найдено;
- какое решение применяется;
- что сохраняется.

Не говори, что работа завершена, пока результат не подтверждён повторным чтением файла.

Исправление пользователя по тексту, названию, области или семантике имеет приоритет над предыдущей интерпретацией.

После исправления пользователя:

1. Сформулируй обновлённый фильтр задачи.
2. Проверь уже сделанные изменения на соответствие этому фильтру.
3. Исправь все затронутые экземпляры, а не только указанный пример.
4. Повтори аудит и сообщи новый подтверждённый результат.

Не подменяй точный пользовательский текст более коротким или «улучшенным» вариантом. Структурная работа не даёт права редактировать текст.

### При визуальном отклонении

1. Останови текущую партию.
2. Назови конкретное отклонение.
3. Восстанови исходную геометрию или согласуй изменение.
4. Повторно проверь экран.
5. Только затем продолжай.

### При ошибке операции

1. Не повторяй создание вслепую.
2. Прочитай ошибку.
3. Проверь текущее состояние.
4. Определи, была ли операция атомарно отменена.
5. Повтори только минимальное исправленное действие.
6. Снова проверь структуру и скриншот.

### Журнал изменений

Во время задачи отслеживай:

- ID созданных узлов;
- ID изменённых узлов;
- ID удалённых узлов;
- ID наборов компонентов и вариантов;
- созданные или удалённые переменные и стили;
- экраны и секции с новыми инстансами.

Журнал нужен для аудита и точечного исправления, но итоговый ответ должен содержать только полезную пользователю часть.

## Запрещённые подходы

Не допускается:

- создать компонент и оставить требуемые обычные несвязанные копии;
- использовать абсолютное позиционирование как универсальное решение;
- менять внешний библиотечный мастер-компонент;
- отсоединять доступный библиотечный экземпляр;
- смешивать разные семейства в одном аудите;
- создавать токены без реального повторного использования;
- менять пользовательский контент без запроса;
- удалять старый мастер-компонент до аудита потребителей;
- сообщать о завершении без проверки;
- сохранять дробные размеры после нормализации;
- переносить свойства обёртки механически;
- считать любой одноэлементный контейнер ошибкой;
- создавать компонент-обёртку без добавленной функции;
- продолжать массовую замену после визуального отклонения;
- объявлять весь файл очищенным после локального аудита;
- выдавать запланированное изменение за выполненное;
- публиковать изменения без разрешения;
- включать в отчёт соседние типы сущностей, когда пользователь ограничил семейство;
- снимать координаты исходника после вставки, вызвавшей перестройку;
- открывать свойство `TEXT` без связанного ресурса, если это создаёт неверные сочетания;
- округлять внутреннюю геометрию иконок, QR, SVG или библиотечных компонентов;
- создавать отдельный публичный компонент, когда достаточно нового варианта существующего набора без нарушения контракта;
- считать обновление мастер-компонента доказательством обновления обычных элементов на экранах;
- ссылаться в итоговом отчёте только на удалённый исходный узел;
- сводить многоэлементного потребителя к одному новому экземпляру без явного изменения содержимого;
- заменять индикаторы состояния, кольца прогресса, логотипы и декор библиотечными иконками только из-за малого размера;
- объявлять внедрение завершённым после проверки одних экземпляров без широкого поиска обычных похожих элементов;
- группировать документацию по совпадению слова в имени, игнорируя семантический домен;
- считать снимок исходного состояния безусловно актуальным после серии изменений;
- продолжать изменение, если текущее условие уже расходится со снимком;
- исправлять вариант только ради ожидаемого счётчика без проверки текущего содержимого;
- позволять документации с Auto Layout незаметно растягивать мастер-компоненты и объединять их без повторного измерения;
- считать отдельный снимок прозрачного компонента достаточной визуальной проверкой.

## Критерии завершения

Задача завершена, если:

- согласованный компонент или системное изменение существует;
- реальные потребители обновлены в согласованной области;
- содержимое и переопределения сохранены;
- библиотечные элементы остаются инстансами;
- переменные и стили привязаны корректно;
- Auto Layout работает на реальном контенте;
- обычные несвязанные копии не найдены повторным поиском;
- исключения классифицированы;
- затронутые экраны проверены;
- итог подтверждён чтением структуры и визуальной проверкой;
- текущие имена страниц и секций перечитаны после возможных переименований;
- новый API компонента не допускает очевидно несогласованных пар связанных данных;
- итоговые ID мастер-компонентов и экземпляров или ссылки действительно открываются;
- составные элементы сохранили количество, порядок, тексты и состояния каждого элемента;
- после внедрения иконок каждый графический тип классифицирован, а исключения названы;
- точный и широкий повторные поиски выполнены по всей согласованной области;
- организационная правка дизайн-системы сохранила ID мастер-компонентов и не создала сломанных экземпляров;
- итоговое распределение по вариантам и состояниям сверено, а каждый неожиданный выброс проверен по текущему содержимому.

## Формат итогового отчёта

Сообщи:

1. Что создано или обновлено.
2. Какие варианты и свойства доступны.
3. Сколько элементов найдено и заменено.
4. Какие переменные, стили и библиотеки используются.
5. Какие экраны или секции затронуты.
6. Что показал повторный аудит.
7. Какие исключения сохранены и почему.
8. Какие кандидаты можно систематизировать дальше.
9. Если изменялся мастер-компонент — сколько потребителей переключено и сколько осталось.
10. Остались ли риски или решения, требующие пользователя.

Итог должен быть проверяемым: компоненты, инстансы и затронутые экраны должны реально существовать в Figma.
